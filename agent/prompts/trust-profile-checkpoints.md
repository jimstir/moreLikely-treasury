# Trust Profile Attributes: Comprehensive Review

This document provides a deep dive into the 8 community-curated Trust Profile Attributes that the AI Governor evaluates. For each attribute, we break down the risk, the exploitation vector, how the platform catches it, the exact data sent to the LLM, and the probability of malicious intent.

---


> **Architectural Note on UI Display:** 
> The Trust Profile does *not* display individual severity levels. Instead, the UI displays one master **"Alert: Review Required"** flag if any attribute is triggered. 
> The UI calculates an **Overall Probability of Malicious Intent %** based on the aggregate of all triggered attributes. 
> Underneath the master flag, the user can see exactly which attributes were triggered and read the specific descriptions generated by the LLM.

## 1. Owner Governance Override

*   **Explanation:** The treasury owner holds special privileges to forcefully close active proposals (`proposalClose()`) before their scheduled end date.
*   **How it is Exploited:** An owner maliciously closes a legitimate, community-supported proposal right before it passes, purely because they disagree with the community's decision (Erratic Interference).
*   **How it is Caught:** The backend indexes the `proposalClose()` function calls and captures the exact `marketSnapshotAtClosure`. If the market was stable, the AI flags the closure as unjustified interference. If the market was crashing rapidly, the AI forgives the closure as a justified protective measure.
*   **LLM JSON Values & Generation:**
    *   `totalProposalsClosedByOwner`: Fetched via the `proposalBook(uint256)` mapping in `AuditInteractionsWidget`.
    *   `closureType`: Extracted from transaction logs (whether ended naturally or via owner override).
    *   `originalProposalTerms.scheduledCloseDate`: Parsed from the off-chain proposal document (since the scheduled end date is not stored on-chain).
    *   `timeOpenBeforeClosureSeconds`: Calculated from block timestamps (closure block time minus creation block time).
    *   `marketSnapshotAtClosure.assetPrices`: Generated using the contract oracle implemented in this project (which uses Chainlink/Uniswap feeds) tied to the exact block timestamp of the `CLOSE` transaction.
*   **LLM Trigger & Output Description:** If the AI determines the closure was unjustified (stable market), it triggers the attribute and outputs: *"Proposal [ID] was forcefully closed by the owner without a corresponding market crash."*

## 2. Token Add Control

*   **Explanation:** The treasury requires community voting (`ADD_TOKEN` proposals) to whitelist new assets for trading or holding.
*   **How it is Exploited:** An owner holds a massive percentage of the DAO's shares (exceeding the quorum threshold). They unilaterally pass a proposal to add a worthless, malicious token they created, bypassing community consent. They then drain the treasury by swapping valuable assets into this worthless token.
*   **How it is Caught:** The platform calculates the owner's voting power against the threshold. It flags if an `ADD_TOKEN` proposal passes with only the owner's vote. Crucially, the AI checks if the added token is a recognized safe asset (`isVerifiedBlueChip`).
*   **LLM JSON Values & Generation:**
    *   `ownerVotingPowerPercentage`: Calculated by dividing `balanceOf(owner)` by `totalSupply()` on the `TreasuryToken` contract.
    *   `votingThresholdPercentage`: Read from the `votingThres()` state variable.
    *   `hasUnilateralControl`: Boolean evaluated if owner's voting power exceeds the threshold.
    *   `tokenAdded.isVerifiedBlueChip`: Evaluated by checking if the contract address exists on standard Uniswap default token lists.
    *   `passedUnilaterallyByOwner`: Evaluated by checking if the owner was the sole voter required to pass the proposal.
*   **LLM Trigger & Output Description:** If the owner unilaterally passes a non-blue-chip token, it triggers the attribute and outputs: *"Owner used unilateral voting power to approve an unverified token [Token Name]."* Additionally, the AI outputs a strong recommendation: *"Warning: Exercise extreme caution joining this treasury due to the high concentration of governance tokens held by a single individual."*

## 3. Consensus Quorum Level

*   **Explanation:** The percentage of total shares that must vote "Yes" for a major treasury action to pass.
*   **How it is Exploited:** 
    *   *If too low:* A malicious actor (or small group) waits for a period of low activity and passes a hostile takeover proposal with a tiny fraction of the total supply.
    *   *If too high:* The owner sets the quorum to 99%, making it mathematically impossible for the community to ever pass a proposal, resulting in permanent governance gridlock.
*   **How it is Caught:** The platform compares the `currentVotingThresholdBps` against the `averageVoterTurnoutPercentage`. If average turnout is 10%, but the quorum is 80%, the AI flags the treasury as functionally dead/gridlocked.
*   **LLM JSON Values & Generation:**
    *   `currentVotingThresholdBps`: Fetched directly from the `votingThres()` variable on the Vault.
    *   `totalShareholderCount`: Queried from the indexer tracking unique holders of the `TreasuryToken`.
    *   `averageVoterTurnoutPercentage`: Generated by the backend indexer aggregating total votes cast across all historical proposals.
    *   `failedDueToQuorum`: Extracted from proposal execution revert reasons or failed states.
*   **LLM Trigger & Output Description:** If historical turnout is significantly lower than the quorum, it triggers the attribute and outputs: *"The required voting quorum ([X]%) is mathematically unreachable based on historical voter turnout ([Y]%), resulting in governance gridlock."*

## 4. Strategy Rebalancing & Asset Deviation Risk

*   **Explanation:** The owner/agent has permission to execute `swapBack()` functions to rebalance the portfolio according to the Mandate's target allocations.
*   **How it is Exploited:** The owner executes a proposal to acquire a safe asset (USDC), but secretly uses `swapBack()` later to trade the USDC into an unapproved, highly volatile meme-coin that deviates entirely from the Treasury Mandate goals.
*   **How it is Caught:** The indexer tracks all `SwapExecuted` events. The AI compares the `tokenBought` against the `treasury-mandate.md` target allocations to ensure the trades are strictly for rebalancing approved assets.
*   **LLM JSON Values & Generation:**
    *   `totalSwapBacksExecuted`: Generated by indexing all `SwapExecuted` events emitted by the specific Policy contract.
    *   `portfolioDeviationFromMandatePercentage`: Calculated by comparing current balances against the tokens explicitly authorized in passed proposals.
    *   `tokenSold` & `tokenBought`: Parsed directly from the swap event logs.
    *   `isTokenBoughtInApprovedProposals`: Calculated by cross-referencing the `tokenBought` against the list of tokens approved by the community.
*   **LLM Trigger & Output Description:** If the bought token is not in the mandate, it triggers the attribute and outputs: *"Portfolio rebalancing was executed to acquire [Token Name], which severely deviates from the approved Treasury Mandate."*

## 5. Lending Policy Default-Risk Management

*   **Explanation:** If the treasury issues loans, those loans must be monitored. If a borrower's collateral drops in value, the debt must be instantly liquidated to protect the treasury.
*   **How it is Exploited:** The treasury relies on manual human monitoring instead of an AI Governor. A flash crash occurs at 3 AM. The human is asleep, fails to call `seizeCollateral()`, and the treasury absorbs massive bad debt. Alternatively, the owner claims an AI is running, but they never actually deployed it.
*   **How it is Caught:** The platform audits if an AI is actively deployed. It checks for valid 0G Network or platform receipts proving the AI Governor is active for lending tasks. If no AI is verified, and humans are slow to liquidate, it flags a severe risk.
*   **LLM JSON Values & Generation:**
    *   `agentVerificationReceipt`: Generated by checking the 0G Network or Platform deployment logs to mathematically prove the AI Governor is actively deployed for lending tasks.
    *   `isAiGovernorAuthorized`: Generated by passing the verified AI Agent wallet to the Vault's `getAuth(address)` mapping.
    *   `totalActiveLoans` & `loansInDefaultWarning`: Fetched from the Lending Policy contract state.
    *   `timeSpentInDefaultWarningSeconds`: Generated by tracking the block timestamp when a loan's health factor dropped below 1.0 against the timestamp of the actual liquidation tx.
*   **LLM Trigger & Output Description:** If bad debt sits unliquidated, it triggers the attribute and outputs: *"Loans remained in default warning for [X] seconds before liquidation."* If no AI receipt is found, it outputs: *"No verified AI Governor deployment found for lending tasks; relying on manual human intervention."*

## 6. Unified Policy Access Control

*   **Explanation:** The Treasury Vault is the master contract. Policy contracts (like Swap or Lending) should query the Vault to see who the authorized owner/agent is.
*   **How it is Exploited:** A standalone policy contract uses its own hardcoded `owner` variable instead of querying the Vault. The DAO votes to replace a malicious owner on the Vault, but the malicious owner secretly retains keys to the Swap Policy contract, creating a backdoor to drain funds.
*   **How it is Caught:** The backend compares the master `vaultOwnerAddress` against the local permissions of every active policy contract. The AI flags if any policy is dangerously "fragmented" or out of sync.
*   **LLM JSON Values & Generation:**
    *   `vaultOwnerAddress`: Fetched by calling `tOwner()` on the master Vault contract.
    *   `totalActivePolicies` & `policiesWithFragmentedAccess`: Evaluated by scanning registered policy contracts.
    *   `localOwnerDiffersFromVault`: Generated by comparing `tOwner()` on the Vault against the `owner` state variable on the standalone policy contract.
    *   `lastAccessControlUpdateTimestamp`: Fetched from ownership transfer event logs.
*   **LLM Trigger & Output Description:** If a policy has a different owner, it triggers the attribute and outputs: *"The [Policy Name] contract has fragmented access control and is not securely synced to the master Treasury Vault."*

## 7. Unapproved Token & Collateral Additions

*   **Explanation:** The owner can temporarily register tokens to a policy contract so they are ready to trade *after* the community approves the associated proposal.
*   **How it is Exploited:** The owner registers a token, initiates a vote, but begins aggressively trading that token *before* the voting period ends (front-running the vote). Alternatively, they tell the community they are voting to add a safe token, but actually register and trade a completely different, unapproved token.
*   **How it is Caught:** The backend scans the policy contract's token mappings and compares them against the actual proposal states in the `TreasuryVault`. The AI reads the off-chain proposal description to verify the token being traded was actually what the community was voting on.
*   **LLM JSON Values & Generation:**
    *   `totalTokensOnPolicyContracts` & `unapprovedOrphanedTokens`: Evaluated by scanning the token mappings on policy contracts.
    *   `associatedProposalId` & `proposalState`: Queried from the Vault's proposal state.
    *   `offChainProposalDescription`: Parsed from the off-chain document tied to the proposal ID, allowing the AI to read what the owner told the community.
    *   `hasBeenTradedBeforeApproval`: Generated by finding the token in `collateralProposalIds`, verifying the Vault proposal is still `pending`, and checking the policy contract for transfer/swap events.
*   **LLM Trigger & Output Description:** If traded before approval, it triggers and outputs: *"Active front-running detected: [Token Name] was traded while Proposal [ID] was still pending."* If not in the description, it outputs: *"[Token Name] swap was not described/shared in any open proposal description."*

## 8. Deposit Token Asset Diversity & Decimal Risk

*   **Explanation:** The treasury accepts various tokens from users joining the DAO (e.g., USDC, DAI).
*   **How it is Exploited:** 
    *   *Math Exploit:* The treasury accepts 6-decimal USDC and 18-decimal DAI in the same pool without proper normalization math, allowing a depositor to trick the contract into minting trillions of shares for pennies.
    *   *Economic Exploit:* The treasury accepts a highly volatile token alongside stablecoins. A malicious user deposits the volatile token right before it crashes, socializing their massive losses onto the existing shareholders.
*   **How it is Caught:** The indexer queries `getApprovedTokens()` and maps their decimals and fiat pegs. The AI flags if a mathematically dangerous decimal mismatch exists, or if fiat values wildly diverge without oracle protection.
*   **LLM JSON Values & Generation:**
    *   `approvedDepositTokens` (with `symbol`, `decimals`, `currentPegValueUSD`): Generated by querying `decimals()` on every ERC20 address in the `approvedTokens` array and checking their oracle values.
    *   `hasDecimalMismatch`: Evaluated by comparing the decimals of all approved tokens (e.g., 18 vs 6).
    *   `hasFiatValueMismatch`: Evaluated by comparing the peg values retrieved from the contract oracle.
*   **LLM Trigger & Output Description:** If decimals mismatch, it triggers and outputs: *"Vault accepts tokens with mismatched decimals ([X] vs [Y]), exposing proportional math to exploitation."* If fiat values mismatch, it outputs: *"Vault accepts un-pegged volatile assets alongside stablecoins without oracle normalization."*
